SplitWise

Aplicación web para la gestión colaborativa de gastos compartidos. Permite crear grupos, registrar gastos, dividirlos en partes iguales entre los miembros, registrar pagos y llevar un balance claro de quién debe cuánto a quién.

Qué problema resuelve

Cuando un grupo de personas comparte gastos (viajes, alquiler, salidas, etc.), es difícil llevar la cuenta de quién pagó qué, cuánto consumió cada uno y quién le debe a quién. SplitWise resuelve esto con un modelo simple:

  • Grupo como contenedor de personas y gastos.
  • Gasto con división igualitaria automática.
  • Pago como transferencia directa entre miembros.
  • Balance que muestra saldos y sugiere transferencias.
  • Reportes con exportación CSV.

Estado actual del producto

El proyecto está en desarrollo activo. Las fases completas incluyen gestión de grupos, gastos, pagos, balance, roles globales y por grupo, permisos centralizados, medios de cobro, reportes y exportación CSV, y una auditoría de UX reciente. No se implementaron períodos (fase descartada).

Setup local

Requisitos

  • PHP 8.1 o superior (con extensiones mbstring, intl, mysqli, json)
  • Composer
  • MySQL / MariaDB
  • Apache con mod_rewrite
  • Git

XAMPP

El proyecto corre sobre XAMPP. Clonar el repositorio dentro de C:\xampp\htdocs\SplitWise.

Instalación

cd C:\xampp\htdocs\SplitWise
composer install

Archivo .env

Copiar env a .env y ajustar:

CI_ENVIRONMENT = development
database.default.hostname = localhost
database.default.database = splitwise
database.default.username = root
database.default.password =
database.default.DBDriver = MySQLi

Base de datos

Crear la base de datos en MySQL y ejecutar las migraciones:

php spark migrate

Ejecutar tests

php vendor/bin/phpunit --no-coverage

Comandos útiles

php spark routes          # Ver todas las rutas

Email (SMTP)

Para habilitar envío real de correo (recuperación de contraseña, notificaciones), descomentar en .env: 

email.protocol = smtp
email.fromEmail = no-reply@tudominio.com
email.fromName = SplitWise
email.SMTPHost = smtp.gmail.com
email.SMTPUser = tu-email@gmail.com
email.SMTPPass = tu-contraseña-de-aplicación
email.SMTPPort = 587
email.SMTPCrypto = tls

Requiere: protocol=smtp, SMTPHost, SMTPUser y SMTPPass no vacíos.

Con Gmail: fromEmail debe coincidir con SMTPUser. SMTPPass debe ser una contraseña de aplicación (sin espacios).

Comportamiento por ambiente: En development si SMTP no está configurado se muestra un enlace de recuperación en pantalla. Si SMTP falla en producción se muestra un mensaje amigable sin detalles técnicos.

Arquitectura

El proyecto sigue el patrón MVC de CodeIgniter 4, con una capa adicional de servicios para lógica de negocio reutilizable y testeable.

Controllers

Los controladores manejan la entrada HTTP, validan permisos y delegan la lógica a modelos o servicios. Cada controlador suele tener un método por acción: index, new, create, show, edit, update, delete.

Services

Los servicios contienen lógica de negocio que no pertenece estrictamente a un modelo o controlador:

  • GroupPermission — verifica permisos por rol de grupo y estado.
  • Reportes — consultas agregadas para reportes y exportación CSV.

Views

Las vistas usan PHP embebido con Bootstrap 5.3. Siguen un patrón consistente: _head.php + _navbar.php + contenido + _footer.php. Mobile responsive con clases d-none d-md-block y d-md-none.

Filters

CodeIgniter aplica filtros antes de que una ruta llegue al controlador:

  • csrf — protege formularios POST, PUT, DELETE.
  • auth — redirige al login si no hay sesión activa.
  • admin (AdminFilter) — permite solo usuarios con rol global admin.

Config

Las rutas se definen en app/Config/Routes.php. Las migraciones en app/Database/Migrations/. La configuración de base de datos en .env.

Relaciones importantes

  • grupo_miembros vincula users con grupos (N:M).
  • gastos.pagador_id → users.id (quién pagó).
  • gastos.grupo_id → grupos.id (a qué grupo pertenece).

  • pagos.pagador_id / receptor_id → users.id.
  • pagos.grupo_id → grupos.id.
  • gastos.categoria_id → categorias.id.

Categoría protegida «Otros»

La categoría con nombre Otros es la única protegida. No se puede editar, desactivar ni eliminar. Se usa como valor por defecto cuando un gasto no tiene categoría asignada. Está definida en la migración y se verifica en el controlador de categorías.

Flujos funcionales

Login

El usuario ingresa email y contraseña. El sistema verifica las credenciales y crea la sesión con userId, userName, userEmail y userRole. Si ya hay sesión activa, redirige al dashboard. El logout destruye la sesión.

Dashboard

Muestra un resumen de grupos activos/cerrados/liquidados, saldo global, la lista de grupos del usuario con saldo y deudas pendientes, y los últimos gastos y pagos registrados. Es la pantalla de inicio después del login.

Crear grupo

El usuario completa nombre y descripción del grupo, selecciona miembros iniciales y queda como administrador. El grupo se crea en estado activo.

Agregar miembros

Desde la pantalla de detalle del grupo, los administradores pueden agregar miembros existentes del sistema mediante un selector. También pueden cambiar roles (admin ↔ member) y quitar miembros (si no tienen movimientos y no son el último admin).

Crear gasto

Se selecciona grupo (o viene pre-seleccionado), se ingresa descripción, monto, fecha, categoría (opcional), pagador y participantes. El monto se divide en partes iguales entre los participantes seleccionados. El pagador puede ser también participante.

Editar gasto

Solo el pagador original o un admin del grupo puede editar un gasto. Los cambios se aplican únicamente si el grupo está activo.

Registrar pago

Se selecciona grupo, pagador (quien entrega el dinero), receptor (quien lo recibe), monto, fecha y descripción opcional. Se usa para saldar deudas entre miembros.

Balance

Muestra por cada miembro del grupo cuánto pagó en gastos, cuánto consumió, pagos enviados/recibidos y saldo resultante. Además muestra las transferencias sugeridas: quién le debe a quién y cuánto.

Transferencias sugeridas

El balance calcula automáticamente las deudas netas entre miembros. Desde la pantalla de balance, se puede hacer clic en «Pagar» para ver los medios de cobro del acreedor y registrar el pago directamente.

Medios de cobro

Cada usuario puede registrar sus medios de cobro (alias Mercado Pago, CBU/CVU, link de pago, banco). Se muestran al acreedor cuando alguien quiere pagarle desde la pantalla de balance. Incluye botones de copiar al portapapeles.

Reportes

La pantalla /reportes muestra un resumen global (total gastado, pagado, recibido, saldo), gastos agrupados por categoría y por grupo, y últimos movimientos combinados (gastos + pagos). Se puede filtrar por grupo, categoría y fechas, y exportar a CSV.

Cierre / liquidación de grupo

Un admin puede cerrar un grupo activo (→ cerrado). En estado cerrado no se pueden crear gastos, solo pagos para saldar deudas. Cuando no quedan deudas pendientes, se puede liquidar (→ liquidado), que es el estado final.

Permisos

SplitWise tiene dos sistemas de permisos que operan en paralelo:

Rol global (sistema)

RolAcceso
adminAccede a ABM de usuarios y categorías. No tiene permisos especiales sobre grupos ajenos.
userAcceso normal a grupos, gastos, pagos, reportes y medios de cobro propios.

El filtro AdminFilter protege las rutas de administración (/usuarios/*, /categorias/*).

Rol de grupo

RolPermisos
adminEditar/eliminar grupo, cambiar estado, agregar/quitar miembros, cambiar roles, crear/editar/eliminar cualquier gasto o pago.
memberCrear gastos y pagos. Editar/eliminar solo gastos y pagos propios.

Service GroupPermission

El servicio App\Services\GroupPermission centraliza las reglas de permiso por grupo combinando rol de grupo y estado:

  • Rol: admin puede todo; member solo acciones propias.
  • Estado: activo permite todo; cerrado bloquea gastos; liquidado bloquea todo.

Reportes

La funcionalidad de reportes permite al usuario ver un resumen financiero global de todos sus grupos. El servicio App\Services\Reportes ejecuta consultas SQL directas (Query Builder) para agrupaciones y totales que el modelo existente no soporta.

Qué muestra /reportes

  • Resumen global: total gastado, pagado, recibido, consumido y saldo.
  • Gastos por categoría: cantidad y total agrupados.
  • Gastos por grupo: cantidad y total agrupados.
  • Últimos movimientos: gastos y pagos combinados, ordenados por fecha.

Filtros

Todos los reportes respetan los filtros seleccionados: grupo, categoría, fecha desde/hasta.

Exportación CSV

/reportes/exportar descarga un archivo CSV con los gastos filtrados, incluyendo fecha, grupo, categoría, descripción, pagador y monto. El archivo incluye BOM UTF-8 para compatibilidad con Excel en español.

Alcance por usuario

Todos los reportes limitan los datos a los grupos donde el usuario es miembro (mediante JOIN con grupo_miembros). Un usuario no puede ver datos de grupos a los que no pertenece.

Lógica pura testeable

El método formatearFilasCsv() recibe un arreglo y devuelve las filas formateadas para CSV. No depende de base de datos, lo que permite testearlo sin conexión a DB. El resto de los métodos requieren conexión real a MySQL; en entorno de testing se requiere SQLite3 que no está instalado, por lo que esos tests se omiten.

Entorno de testing: No hay SQLite3 instalado en el entorno de desarrollo. Todos los tests que requieren base de datos se omiten. Se testea solo lógica pura (formato CSV, estructura de métodos).

Testing

Cómo correr tests

php vendor/bin/phpunit --no-coverage

Qué cubren

Los tests en tests/unit/ cubren:

  • PermisosGrupoTest — reglas de permiso por rol, estado, ownership.
  • ReportesTest — formato de filas CSV, existencia de métodos, estructura de datos.
  • Dashboard test — resumen financiero puro, transiciones de estado, reglas de miembros.
  • Auth test — login, logout, sesión, role check.

Por qué se evita SQLite

El entorno de testing de CodeIgniter 4 usa SQLite3 por defecto cuando no hay base de datos configurada. La extensión sqlite3 no está instalada en PHP. Como alternativa, los tests de lógica pura (métodos estáticos que no dependen de DB) se escriben con datos mock en arreglos.

Convención: Los métodos de lógica de negocio que no requieren base de datos se definen como static y se testean con datos en memoria. Los métodos que requieren DB se mantienen sin test unitario o se marcan como @group integration.

Troubleshooting

CSRF vencido

Si un formulario muestra error de CSRF, recargar la página y volver a enviar. Ocurre cuando la sesión expira mientras se completa un formulario largo.

Sesión vencida

La sesión de CodeIgniter tiene un tiempo de expiración configurable en .env (session.expiration). Si la sesión vence, el filtro auth redirige al login.

Migraciones

Si php spark migrate falla, verificar que la base de datos exista y que las credenciales en .env sean correctas. Para resetear: php spark migrate:refresh (borra todos los datos).

XAMPP

Apache debe tener mod_rewrite habilitado para que funcionen las rutas amigables. En XAMPP suele estar activo por defecto. Verificar en httpd.conf que AllowOverride esté en All para el directorio del proyecto.

Encoding / Mojibake

Si aparecen caracteres extraños («Ã¡» en lugar de «á»), verificar que el archivo .env tenga charset = utf8mb4 y que la base de datos use utf8mb4_unicode_ci. Las vistas usan <meta charset="UTF-8">.

Permisos de usuario/admin

Si un usuario normal ve la pantalla de administración, el filtro AdminFilter debería bloquearlo. Si no funciona, verificar que el rol esté correctamente asignado en la tabla users (role = 'admin' o 'user').
